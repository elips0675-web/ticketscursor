Оценка проекта Service Desk
Итоговая оценка: 6.5/10
Проект амбициозный и функционально богатый, но между заявленным состоянием в документации и фактическим содержимым файлов — системные расхождения. Ниже — по осям из AGENTS.md.

🔴 Критические проблемы (P0) — документация лжёт о фиксах
1. scripts/check-bundle-size.js — ESM/CommonJS конфликт НЕ исправлен
Что-доделать.txt (P0 #3) утверждает: «Исправлено (import { gzipSync })». Фактически в файле:

js
const gzipSize = require('zlib').gzipSync(content).length
package.json содержит "type": "module" → require упадёт с ReferenceError: require is not defined in ES module scope. CI job bundle сломан.

2. CI: cmd /c на Ubuntu НЕ исправлен
Что-доделать.txt (P0 #1) утверждает: «Исправлено (working-directory: server)». Фактически в ci.yml:

yaml
- run: cd server && cmd /c "npx vitest run 2>&1"
  env:
    DATABASE_URL: mysql://root:test@localhost:3306/service_desk
cmd /c — Windows-only команда, на ubuntu-latest job test падает сразу.

3. K6: dev-login на каждой итерации НЕ исправлен
Что-доделать.txt (P1 #5) утверждает: «Kimi ошибся, TOKEN из env, не dev-login». Фактически test/load/tickets.k6.js:

js
export default function () {
  const loginRes = http.post(`${BASE_URL}/api/auth/dev-login`, ...)
Логин на каждой из ~30 итераций. Это искажает нагрузочный профиль (auth становится доминирующей нагрузкой).

4. express-validator и prisma в dependencies НЕ убраны
Что-доделать.txt (P1 #2, #3) утверждает: оба удалены / перемещены. Фактически server-package.json:

json
"dependencies": {
    "express-validator": "^7.3.2",   // ← должен быть удалён
    "prisma": "^5.22.0",              // ← должен быть в devDeps
    "knex": "^3.3.0"                  // ← дублирующий ORM
}
express-validator в зависимостях — мёртвый вес ~200KB + CVE-риски.

5. Playwright job в CI — сервер запускается некорректно
yaml
- run: cd server && node src/index.js &
- run: npm run build
- run: npx vite preview --port 5173 &
- run: npx playwright test
Между запуском сервера и тестами нет ожидания готовности (нет wait-for-it, нет healthcheck-loop). На медленном runner'е тесты начнутся до старта БД → flaky.

6. docker-compose.yml vs Dockerfile — конфликт build-контекста
yaml
app:
  build: .        # контекст = корень
dockerfile
COPY --from=builder /app/server ./server
RUN cd server && npm ci --production
В builder-стейдже копируется COPY package*.json ./ (только корневые), но не копируется server/package.json — npm ci в server/ упадёт без package-lock.json. Multi-stage сломан.

🟡 Важные проблемы (P1)
7. CHANGELOG.md структурно повреждён
[1.9.0] — 2026-09-19 стоит дважды (первый — пустой, второй — с контентом)

[2.1.0] и [2.0.0] стоят выше [1.9.0] с контентом, но ниже пустого [1.9.0]

При этом package.json = 1.9.0, а CHANGELOG описывает 2.1.0

Файл обесценивает сам себя. Нельзя использовать как источник правды.

8. README противоречит сам себе
Где	Что заявлено
Таблица сверху	Coverage (клиент) — 71% stmts
Таблица файлов	«thresholds 71/61/61/74»
vitest.client.config.ts	72/62/62/75
Что-доделать.txt (Этап 39)	«Поднять до 72/62/62/75»
Три разных числа в одном репозитории.

9. docker/entrypoint.sh — «мёртвый файл»
README утверждает: «Dockerfile: entrypoint.sh не скопирован → Файл удалён из репо». Но infra.txt содержит его содержимое. Значит, файл либо есть (тогда README врёт), либо его нет (тогда зачем он в infra.txt?). Не определиться с источником правды.

10. E2E — 90% smoke-only
README: «E2E smoke-only — Исправлено, добавлен user-flow.spec.ts». Фактически в e2e-tests.txt:

ts
test('renders tickets list', async ({ page }) => {
  await page.goto('/tickets')
  await expect(page.locator('h1, h2, h3').first()).toBeVisible()
})
Проверяется только наличие любого заголовка. Тест пройдёт даже если страница показывает «Ошибка 500». Это не тест, а иллюзия теста. Единственный реальный тест — global-setup.ts (проверяет получение токена).

11. test-e2e-api.js — тест на несуществующий контракт
js
const { status, data } = await api('GET', '/api/health')
assert(data.success === true, 'Expected success: true')
Но в CHANGELOG v1.0.0 сказано, что /api/health возвращает prometheus-формат (в контексте GET /api/metrics). Контракт {success: true} для health — не подтверждён нигде в коде сервера.

12. vitest.client.config.ts не покрывает новые модули
include: ['src/test/**/*.test.{ts,tsx}'] — но useFeature.test.tsx в src/test/, ок. Однако CommandPalette.tsx, AdminRules.tsx, AdminIntegrations.tsx, SSO.tsx — новые фичи Этапа 34-35, ни одного теста для них в test-inventory.json не видно.

Топ-5 действий (в порядке приоритета)
Починить check-bundle-size.js → import { gzipSync } from 'zlib'

Убрать cmd /c из CI → run: cd server && npx vitest run

Убрать express-validator + prisma из server deps (перенести в devDeps)

Починить Dockerfile → COPY server/package*.json ./server/ && RUN cd server && npm ci

Починить CHANGELOG → один [1.9.0] в начале, [2.1.0] → [1.10.0], [2.0.0] → [1.9.1] (не прыгать мажор без причины)

Главный вывод
Проект сильнее, чем средний пет-проект (стек, архитектура, охват фич), но слабее, чем заявляет о себе в README и Что-доделать.txt. Ключевая проблема — документация-самоотчёт не соответствует коду. Это опаснее, чем просто баги: новый разработчик (или AI-аудитор) не может доверять файлам состояния.

Рекомендация: перестать писать «✅ Исправлено» в Что-доделать.txt до того, как фикс виден в самом файле, а не только в отчёте. Ввести чек-лист: «фикс подтверждён grep'ом по файлу X, строка Y».

Реальная оценка: 6.5/10. Потенциал — 8.5/10. Разрыв — в гигиене и честности документации.
