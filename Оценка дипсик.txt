Оценка проекта Service Desk
Общий вердикт: 7.5 / 10
Проект сильный, зрелый, не «домашка». По функциональности обгоняет многие опенсорсные helpdesk’и (Zammad, osTicket). Но есть несколько реальных багов инфраструктуры, которые «подтачивают» впечатление. AI-аудиты (Kimi 6.5, Qwen 8.5, DeepSeek 7) в целом правы, но с перекосом: Kimi недооценил, Qwen переоценил.

Что реально сильно (8–9 / 10)
Продуктовая зрелость. 25 Prisma-моделей, 90+ эндпоинтов, SSO/OIDC, Webhooks + HMAC, API-токены, Rules Engine, Recurring Tickets, Collision Avoidance, Public Portal, IMAP ingestion, CSAT, SLA pause + business hours, Time tracking, Read receipts, Outbox Pattern, DLQ. Это уровень коммерческой системы, а не пет-проекта.

Архитектура. Сервисный слой, слоистая структура (routes → services → prisma), Zod-валидация, RBAC 5 ролей с иерархией (super_admin проходит всё), идемпотентные миграции, graceful shutdown. Всё как надо.

Тесты. 1008 тестов (485 клиент + 523 сервер), реальные интеграционные с Supertest + MySQL, MSW для фронта, Playwright. Не стабы.

Инфраструктура. CI с 6 job’ами, Docker multi-stage, K8s манифесты, Prometheus + Grafana, k6 + Artillery, Redis adapter для Socket.IO с fallback, Meilisearch с fallback на FULLTEXT → LIKE. Отлично.

Документация. CHANGELOG (v0.1 → v2.1), context.txt, AGENTS.md, PLAYBOOK, дорожная карта. Редкость.

Что реально плохо (баги, не мнения)
🔴 1. Dockerfile + docker-compose.yml — прямая поломка
dockerfile
FROM node:22-alpine AS builder
FROM node:22-alpine AS server   # ← сервер
FROM nginx:alpine AS frontend   # ← последний = по умолчанию
docker-compose.yml:

yaml
app:
  build: .                # соберёт ПОСЛЕДНИЙ стейдж = frontend (nginx)
  ports: ['4000:4000']    # а nginx слушает 80
Сервис app запустит nginx и будет проксировать на app:4000, которого нет. Нужно build: { context: ., target: server }. Это критично.

🔴 2. CI job test сломан
yaml
- run: cd server && cmd /c "npx vitest run 2>&1"
cmd /c — это Windows. CI на ubuntu-latest. Тесты сервера в CI не запускаются. Нужно working-directory: server + обычный npx vitest run.

🔴 3. scripts/check-bundle-size.js не запустится
js
import { readFileSync } from 'fs'   // ESM
...
const gzipSize = require('zlib').gzipSync(content).length  // require в ESM
package.json имеет "type": "module" → require undefined → catch съест ошибку и скрипт всегда вернёт «OK». Bundle-check в CI — фиктивный.

🔴 4. vitest-конфиг
README честно пишет: 86/570 тестов падают из-за отсутствия vitest.config.ts. vitest.client.config.ts есть, но дефолтный vitest.config его не подхватывает. npm test фронта работает только потому что явно передаёт --config. А в CI и в server/ — нет.

🟡 5. nginx-конфиг в Dockerfile-стейдже
dockerfile
FROM nginx:alpine AS frontend
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx/default.conf /etc/nginx/conf.d/default.conf
proxy_pass http://app:4000 — но в этом контейнере нет никакого «app». Ок, если рядом есть сервис app, но см. пункт 1 — он не поднимется. Двойная поломка.

🟡 6. docker/entrypoint.sh не используется
Dockerfile не содержит ENTRYPOINT/COPY entrypoint.sh, а docker-compose.yml тоже. Мёртвый код.

🟡 7. E2E — smoke-only (аудит прав)
99% тестов — expect(page.locator('h1, h2, h3').first()).toBeVisible(). Это не тесты, а «страница не белый экран». Заявленные «36 тестов» не проверяют ни одного пользовательского сценария. Один user-flow.spec.ts (по README) чуть глубже, но в e2e-tests.txt он не попал.

🟡 8. Рассинхрон источников
README.md: k6 в k6/

load-tests.txt: k6 в test/load/

context.txt: 485 тестов, README: 485, Что-доделать: 86/570 — три разных числа

frontend-tests.txt сам признаёт, что 556 строк hook-тестов — галлюцинация

Это значит, что источник правды не один. Плохо для передачи проекта.

🟡 9. Технический долг
Knex + Prisma одновременно — 3 файла миграций + knexfile.js в scripts. Мертвечина.

prisma в dependencies сервера — должен быть в devDependencies.

@aws-sdk/* + multer + meilisearch + bullmq в dependencies, но используются опционально — тянет 100+ МБ.

Coverage 71% — цель 80%, но на таком объёме это 2–3 недели точечной работы.

❌ Что НЕ работает (и ты это, скорее всего, не проверял)
1. docker compose up -d — поднимет nginx вместо API
yaml
app:
  build: .              # ← соберётся последний стейдж (frontend/nginx)
  ports: ['4000:4000']  # ← nginx слушает 80, порт пустой
Ты запустишь, контейнер «healthy» (порт открыт), но API на 4000 не будет. Фронт будет валиться в 502.

Ты это не заметил, потому что деплоишь локально, а не через Docker.

2. scripts/deploy.ps1 и scripts/docker-deploy.sh — тоже сломаны
Они вызывают docker compose up -d → см. пункт 1. Скрипт напишет «✅ Deployment complete!», а по факту ничего не работает.

3. GitHub Actions — серверные тесты не запускаются
yaml
- run: cd server && cmd /c "npx vitest run 2>&1"
cmd /c — это Windows. На ubuntu-latest команда падает. CI зелёный, но 523 серверных теста в CI не гоняются вообще.

4. Bundle-size check — фиктивный
js
import { readFileSync } from 'fs'    // ESM
require('zlib')                       // ReferenceError
catch глотает ошибку → скрипт всегда пишет «✅ Bundle size OK». Проверки размера бандла нет.

5. 86 из 570 тестов падают
Ты сам это пишешь в README.md и Что-доделать.txt. Причина — нет корневого vitest.config.ts. То есть часть тестов (видимо, те, что запускаются без --config) падает.

Что сделать прямо сейчас (30 минут)
1. Dockerfile — добавить target в compose:

yaml
# docker-compose.yml
app:
  build:
    context: .
    target: server   # ← вот это
И server стейдж должен иметь COPY server/package*.json + npm ci + prisma generate.

2. CI — убрать cmd /c:

yaml
- run: npx vitest run
  working-directory: server
3. Bundle-check — фикс импорта:

js
import { gzipSync } from 'zlib'   // вместо require
...
const gzipSize = gzipSync(content).length
4. Корневой vitest.config.ts:

ts
export { default } from './vitest.client.config'
или просто переименовать vitest.client.config.ts → vitest.config.ts.

После этих 4 правок — «рабочая» станет правдой и для Docker, и для CI.

Приложение — да, боевое. Docker/CI/скрипты — нет, это карго-культ. Пока ты деплоишь через npm run dev и Laragon — всё ок. Как только попробуешь docker compose up на чистой машине — узнаешь о пунктах 1–2 на практике.
