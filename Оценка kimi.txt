Оценка проекта Service Desk (v2.1.0, 21.09.2026)
Общая оценка: 6.5–7 / 10
Функционально проект сильный — уровень зрелости фич выше среднего open-source helpdesk. Но задокументированное состояние и фактическая инфраструктура расходятся в нескольких критичных местах, а документация местами сгенерирована с галлюцинациями.

✅ Сильные стороны (это реально хорошо)
Инженерная база: Outbox Pattern, идемпотентные миграции, graceful shutdown, DLQ с экспоненциальным бэкоффом, CSP через Helmet, health/readiness пробы, audit log. Это уровень продакшн-подхода, а не пет-проекта.
Фичи шире аналогов: collision avoidance, recurring tickets, rules engine, HMAC webhooks, API-токены с SHA-256, двусторонний Telegram-бот, public portal + public KB, CSAT, SLA с бизнес-часами и паузой. Для 1.x-2.x версии — очень плотно.
Дисциплина: check-console после каждого изменения, lint-staged, ErrorBoundaries, единый формат ответов API, Zod-схемы — процесс выстроен.
Хорошие интеграционные тесты ядра: tickets.service (~91%), SLA-матрица, search с фолбэками покрыты осмысленно.
🔴 Критичные проблемы (с доказательствами из файлов)
1. CI нерабочий — cmd /c на Ubuntu
.github/workflows/ci.yml, job test:
yaml
- run: cd server && cmd /c "npx vitest run 2>&1"
cmd — это Windows-интерпретатор. На ubuntu-latest его нет, джоба упадёт мгновенно. Судя по всему, CI либо никогда не гонялся на GitHub, либо всё это время красный. Та же конструкция в Что-доделать.txt указана как «уже исправлено до аудита» — нет, не исправлено.
2. Джобы playwright и e2e-api не могут работать
В playwright джобе не устанавливаются зависимости сервера (только root npm ci), но джоба запускает node src/index.js — сервер не стартует.
node src/index.js & → сразу npm run build → vite preview & → сразу playwright test. Нет wait-on/healthcheck — гонка, флаки гарантированы.
Джоба e2e-api тестирует http://localhost:4000, ничего не поднимая. Всегда падает.
3. docker-compose собирает не тот стадийный образ
Dockerfile — multi-stage, последняя стадия frontend (nginx). В docker-compose.yml сервис app делает build: . без target: → получает nginx вместо node. Порт 4000:4000 маппится на контейнер, где слушается только 80-й. docker compose up = упавший бэкенд.
Дополнительно: docker/entrypoint.sh никуда не подключён (нет COPY/ENTRYPOINT в Dockerfile) — мёртвый код. Обещанные в CHANGELOG redis, prometheus, grafana, meilisearch в compose отсутствуют — серьёзный drift между CHANGELOG и реальностью.
4. scripts/check-bundle-size.js молча не работает
Файл лежит в "type": "module" пакете и использует require('zlib') → ReferenceError при каждом запуске. Всё обёрнуто в try/catch с console.warn → CI-чек всегда мягко проходит, ничего не проверяя. Bundle check — фикция.
🟡 Важные проблемы
Достоверность тестовых инвентарей под вопросом. README заявляет «102 файла / 485 тестов» на фронте, но frontend-tests.txt перечисляет ~25 файлов. server-tests.txt описывает api.test.js как использующий «Bun TestClient + AutoroutingRequest для axios-совместимости» и «LaunchDarkly mock» — ни Bun, ни LaunchDarkly в стеке нет. В time.service.test.js тест с названием felizCumpleaños («с днём рождения» по-испански). Это галлюцинации AI-генерации, и они дошли до README. Сам frontend-tests.txt признаёт: 556 строк предыдущей версии были несуществующими тестами. Вывод: заголовочные цифры нельзя считать подтверждёнными — нужно генерировать инвентарь скриптом, а не руками/AI.
Противоречие по багу #3. Что-доделать.txt: «Server api.test.js падает: POST /api/tickets → 500 вместо 201». При этом везде заявлено «523/523 ✅». Один из этих фактов неверен — нужно установить истину, это блокер доверия ко всем метрикам.
Пороги coverage = текущее покрытие. vitest.client.config.ts: thresholds 71/61/61/74 — ровно зеркало текущего состояния. Такие пороги не защищают от регресса ничего. Цель заявлена 80% — пороги должны быть рачёткой (например, current+2, расти по шагам).
Незакрытый технический долг (частично признан): два ORM (Knex в deps, миграции на knex при выбранном Prisma), двойная валидация (zod + express-validator), prisma CLI в dependencies вместо devDependencies, неподтверждённый статус reply-threading в email ingestion.
Нестыковка версий. CHANGELOG объявляет 2.0.0 и 2.1.0, а оба package.json — всё ещё 1.9.0. scripts/bump-version.js существует, но не использован. Заголовок ## [1.9.0] в CHANGELOG продублирован дважды.
Нагрузочные тесты тестируют не то. k6 делает dev-login на каждую итерацию — замеряется скорость эндпоинта логина, а не тикетов. Нет ни одного POST-сценария, нет WS-нагрузки (при заявленном Socket.IO-ядре). Artillery — один сценарий login→list. Для системы с 90+ эндпоинтами это декоративно.
E2E — почти весь smoke. 36 тестов: «рендерится h1», «кнопка видна». SLA/автоназначение/экспорт проверяются наличием кнопки, а не поведением. Единственный «user-flow.spec.ts (8 тестов)» из README в инвентаре отсутствует. Хорошо как smoke-слой, но это не «E2E расширены до user-flow».
🟢 Мелочи и риски
dev-login без явного выключения в проде — из файлов не видно guard'а по NODE_ENV. Если его нет — это backdoor. Проверить обязательно.
JWT в localStorage (по global-setup видно) — классический XSS-вектор; для корпсистемы стоит хотя бы зафиксировать осознанное решение.
Калькулятор в сервис-деске — не проблема, но выглядит как сирота в навигации.
86 падающих тестов при запуске vitest без флага --config — фикс тривиален (vitest.config.ts рядом), но почему-то всё ещё открыт.
check-console.mjs проверяет 6 страниц по AGENTS.md, но 17 по context.txt — непонятно, какая цифра актуальна.

Резюме
Проект по функциональности и архитектуре — 8.5/10, это честная сильная работа. Но инфраструктура доверия (CI, Docker, метрики) — 3–4/10: пайплайн, который заявлен как зелёный, содержит минимум четыре гарантированных падения, цифры в README не подтверждаются инвентарями, а сами инвентари содержат AI-галлюцинации. Худшее, что можно сделать сейчас, — добавлять новые фичи. Лучшее — один «недостоверность-спринт»: починить CI/Docker, верифицировать метрики скриптами, и тогда 7/10 станут честными 8+.


Честно и коротко: приложение — да, инфраструктура — нет.
Что работает (судя по файлам):
Локальная dev-среда — реально работает: MySQL поднят, API на 4000, Vite на 5173, check-console 17/17, E2E гоняются. Код фич написан и покрыт тестами — это не макет, это живой проект.
Сами тесты, скорее всего, локально проходят (вы же их постоянно запускаете).
Что НЕ работает:
GitHub CI — упадёт на первом же шаге (cmd /c на Ubuntu). Заявленный «зелёный CI» в репозитории, скорее всего, красный или никогда не запускался.
Docker-деплой — docker compose up поднимет nginx вместо node-сервера. В прод через заявленный compose не выйти.
Bundle-size check — молча ничего не проверяет.
Цифры — «523/523 ✅» против «api.test.js падает с 500» в вашем же Что-доделать.txt. Один из этих фактов ложь. Какой — надо проверить руками.
Вердикт:
Разрабатывать локально и пользоваться — можно, это рабочая система.
Доверять метрикам в README и деплоить через CI/Docker как описано — нельзя, это сломано.
Хотите — проверьте прямо сейчас две вещи за 5 минут: git push в ветку и посмотреть статус Actions, и docker compose up --build локально. Результат скажет, я прав или нет.
