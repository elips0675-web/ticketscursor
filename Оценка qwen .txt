Оценка проекта Tickets Service Desk (v1.9.0)
📊 Общая оценка: 8.2 / 10 — крепкий enterprise-уровень
Проект выглядит как зрелая service-desk система с современным стеком и продуманной инфраструктурой. Видно, что над ним работали опытные разработчики. Ниже — детальный разбор.
🏗 Архитектура и стек
Сильные стороны:
Свежий стек: Node 22, React 19, Vite 8, Express 5, Tailwind 4 — всё на передовой
Разделение client/server с независимыми package.json — правильно
Enterprise-набор: Sentry (ошибки), Socket.io (realtime), BullMQ (очереди), Meilisearch (поиск), S3 (файлы), web-push, Telegram-бот, LDAP
UI-кит на Radix + shadcn-подход — доступность и кастомизация из коробки
i18next — интернационализация заложена
Риски / вопросы:
⚠️ Prisma + Knex одновременно — дублирование ORM. Обычно это признак незавершённой миграции. Нужно определиться с одним.
⚠️ В docker-compose.yml нет Redis и Meilisearch, хотя они есть в зависимостях сервера (ioredis, @socket.io/redis-adapter, meilisearch). Локальный запуск через Docker упадёт или будет работать в деградированном режиме.
⚠️ Express 5 всё ещё relatively fresh — стоит проверить совместимость middleware.
🚀 Инфраструктура и CI/CD — 9/10
Что сделано отлично:
Multi-stage Dockerfile (builder → server → frontend) — оптимальный размер образов
Nginx как reverse proxy с поддержкой WebSocket (/ws) и SPA fallback
GitHub Actions с 6 параллельными job'ами: lint, typecheck, test, bundle, playwright, e2e-api
Проверка размера бандла (лимит 2MB gzipped) — защита от деградации
entrypoint.sh с ожиданием MySQL — правильный graceful start
deploy.ps1 и docker-deploy.sh — удобные скрипты для разных ОС
Что подправить:
🐛 В scripts/check-bundle-size.js используется require('zlib') внутри ESM-модуля ("type": "module") — это упадёт в рантайме. Нужен import zlib from 'node:zlib'.
🐛 В CI test job: cd server && cmd /c "npx vitest run 2>&1" — cmd /c это Windows-команда, на ubuntu-latest не сработает. Должно быть просто npx vitest run.
⚠️ Нет job'а для деплоя на прод (только локальный deploy.ps1).
⚠️ Нет бэкапов MySQL в docker-compose.
🧪 Тестирование — 7/10
Структура хорошая:
Unit/интеграционные: Vitest (client + server)
E2E: Playwright — 15 файлов, 36 тестов
API E2E: кастомный скрипт на fetch
Нагрузочные: k6 + Artillery (2 сценария)
Главная проблема — E2E тесты поверхностные:
ts

1234
Почти все 36 тестов — это «страница открылась и что-то отрендерилось». Нет реальных пользовательских сценариев:
❌ Создание тикета → назначение → закрытие
❌ SLA-эскалация
❌ Realtime-чат (Socket.io)
❌ Загрузка файлов
❌ Поиск через Meilisearch
❌ RBAC (кроме одной проверки 403 в API-скрипте)
Нагрузочные тесты:
Есть сценарии для tickets и chat — хорошо
Но TICKET_ID = 'test-ticket-id' — захардкожен, в реальности такого ID нет, тест будет давать 404
Пороги p(95)<500ms — адекватные для internal tool
🔐 Безопасность
Плюсы:
helmet, cors, express-rate-limit — базовая защита есть
JWT + bcryptjs + passport + LDAP
cookie-parser для httpOnly cookies
Чего не хватает:
Нет упоминания CSP-политик в Nginx
Нет rate-limit на /api/auth/dev-login (видно в тестах) — брутфорс-уязвимость
JWT_SECRET: test-secret-key в CI — ок для тестов, но нужно следить, чтобы не попало в прод

🎯 Итог
Это production-ready проект уровня middle+/senior команды. Архитектурные решения современные, CI/CD выстроен грамотно, стек актуальный. Основные проблемы — не концептуальные, а тактические: баги в скриптах CI, неполный docker-compose и поверхностные E2E-тесты, которые дают ложное чувство покрытия.
Если починить указанные мелочи и дописать 5–10 настоящих E2E-сценариев — проект будет на 9/10.
