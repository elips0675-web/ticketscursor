⚠️ Архитектурные долги и риски
🔴 Критично
1. Двойной ORM: Prisma + Knex
В server-package.json есть и prisma/@prisma/client, и knex/mysql2
Это рассинхрон схем, двойная поддержка миграций, путаница в коде
Рекомендация: выбрать один. Prisma — для типобезопасности, Knex — для сложных запросов. Идеально — мигрировать на Prisma полностью, Knex оставить только для миграций/seed.
🟡 Средний приоритет
2. E2E тесты — только smoke
17 страниц проверены на check-console, но реальных user flows мало
Рекомендация: добавить критические сценарии:
Создание тикета → назначение → SLA → закрытие
Real-time чат между двумя пользователями
LDAP login flow
3. Load tests — узкое покрытие
Только tickets и chat
Нет тестов для: auth, search (Meilisearch), file uploads, WebSocket на 1000+ соединений
Рекомендация: добавить сценарий "100 одновременных создателей тикетов" и "WebSocket stress"
4. Coverage 71% — можно выше
Для enterprise-проекта целевой порог — 80%+ statements
Рекомендация: дописать тесты для edge-cases в tickets.service, search.service, background-jobs
🟢 Низкий приоритет, но важно
5. Нет упоминаний:
npm audit / Snyk в CI — security scanning
API versioning (/api/v1/...) — при breaking changes будет больно
Observability кроме Sentry (OpenTelemetry, Prometheus метрики)
Rate limiting — есть express-rate-limit, но нет тестов на его поведение под нагрузкой
Backup strategy — скрипт есть, но нет тестов на восстановление
6. Свежие зависимости — риск breaking changes
zod@4.4, express@5.2, vite@8 — все в первых мажорных/полумажорных версиях
Рекомендация: закрепить lock-файл, добавить Renovate/Dependabot с группировкой обновлений
