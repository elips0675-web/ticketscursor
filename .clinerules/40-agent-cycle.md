# 40 — Агентный цикл (протокол одного шага)

Правила 00/10/20/30 здесь не повторяются: этот файл задаёт **порядок действий**
внутри уже выбранной задачи. Источник задачи — только бэклог, как в 00.

## Цикл шага

1. **RESTATE** — одной строкой: что просят и что считается готовым.
2. **MAP** — `npm run stage:context`, затем `grep` по ID в `Что-доделать.txt`.
   Карта чтения — `30-context-map.md`. Репозиторий целиком не читать.
3. **PLAN** — не больше 3 шагов, один файл на шаг. Показать план до правки.
4. **ACT** — одна правка за шаг, минимальный дифф, стиль соседнего кода.
5. **VERIFY** — `npm run stage:gates`, затем выполнить всё из «ИТОГО».
   Прочитать вывод целиком, а не первую строку. exit 0 — единственный признак «зелено».
6. **REPORT** — что изменено (`file:line`), итоги гейтов, что не проверено.

Источник фактов — только исходный код. Отчёты тестов (`vitest-*.json`),
coverage, логи, `playwright-report` и `test-analysis/` доказательством не
являются: они показывают результат прогона, а не поведение кода.

## Бюджет

- ≤ 5 прочитанных файлов на задачу (жёсткий предел из `30-context-map.md`).
- Один файл кода на шаг; соседние файлы — отдельный шаг, а не «заодно».
- Не печатать файл целиком: только изменённый фрагмент.
- Вывод команды — хвост и ошибки, не вся простыня.

## Поиск и доказательства

- Поиск построчный: `{...}` и `[^)]*` на несколько строк ничего не найдут;
  после двух пустых выдач менять слово или расширение, а не повторять шаблон.
- Точка входа — файл, который реально запускается (`scripts` в `package.json`,
  `server.listen`), а не первое совпадение `main`.
- «X зависит от Y» подтверждается чтением X (импорт, скрипт, конфиг), а не
  догадкой по имени файла.
- «Не найдено» без списка проверенных файлов — не ответ.
- Схема БД — из `.prisma` или `.sql`; `PLAYBOOK.md` и `AGENTS.md` — не
  доказательство фактов о схеме.
- Журналы `Что сделано.txt` и `Что-доделать.txt`, `context.txt`, отчёты
  `vitest-*.json`, `coverage/`, `test-analysis/` — не источник фактов о коде.
  Цитата оттуда отклоняется: журнал фиксирует прошлый прогон, а не поведение
  кода.

## Стоп-правила

- Две неудачные попытки подряд → стоп: показать причину, гипотезы и что уже
  пробовали. Не «долбить» правку наугад.
- Нужен файл, которого нет в `30-context-map.md` и который не открывался →
  не утверждать, что он есть.
- Задача шире 5 файлов → остановиться и попросить сузить (00, п. 1).
- Деньги, доступы, схема БД, деплой, миграции → отдельный шаг с явным
  подтверждением пользователя, без «попутно».
- Тест упал из-за правки → чинить причину, а не тест. Удалять/глушить тест,
  расширять `any`, отключать линтер — запрещено (00, 10).

## Формат ответа

- Сначала «Вывод» — 2–4 строки.
- Затем «Факты» — `file:line` + короткая цитата.
- Затем «Проверено» — команда и её итог (exit code / `ALL OK`).
- Затем «Не проверено» и «Следующий шаг» (один).

## Процедуры

Повторяемые сценарии — в `.clinerules/workflows/`:

| Файл | Когда |
|---|---|
| `brief.md` | незнакомый участок, «где это лежит», старт задачи |
| `fix.md` | воспроизводимый баг или падающий тест |
| `test.md` | закрепить существующее поведение |
| `review.md` | ревью готового diff |
| `refactor.md` | упростить без смены поведения |

Команда `/brief.md` в Cline подставляет файл в чат. Это не отменяет правила
00/20: приоритет у `AGENTS.md` (00, п. «Единственные источники правил»).

## Эвалы комплекта

Read-only срез локальной модели по этому проекту:

```bat
agent-eval.bat --tasks E-01,E-07,E-08,E-09
agent-eval.bat --rescore "E:\3060OllamaClineOpenCode-main\evals\live.json"
```

Скрипты и задачи живут в комплекте `E:\3060OllamaClineOpenCode-main`, проект
не хранит их копию: иначе две версии проверки разойдутся. Ручной прогон в Cline
остаётся источником правды — скрипт не умеет править файлы и читать `git diff`.
