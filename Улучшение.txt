Ваш список доработок для TicketsCursor — это отличный план по созданию зрелого и конкурентоспособного продукта. Ориентир на Chatwoot в данном случае очень уместен, так как это эталонная open-source платформа в этой нише. Ниже — анализ того, как архитектура и подходы Chatwoot могут помочь в реализации каждого из ваших пунктов.

🏗️ 1. Стабилизация инфраструктуры и CI/CD
Chatwoot служит хорошим примером зрелого подхода к инфраструктуре.

ESLint Warnings: В качественных open-source проектах, как правило, поддерживается нулевой уровень предупреждений в CI. Это достигается за счет строгой конфигурации правил и их постепенного, но полного устранения. Рекомендую не просто «очистить» логи, а добавить в пайплайн шаг с флагом --max-warnings=0, чтобы предотвратить появление новых предупреждений.

Кроссплатформенный запуск: Chatwoot активно использует Docker и Docker Compose для обеспечения кроссплатформенности и простоты локальной разработки. Вместо .bat-файла лучше развивать подход с docker-compose.dev.yml (или Makefile, который вызывает docker compose), добавив в него тома (volumes) для горячей перезагрузки. Это современный и надежный стандарт.

Health Checks: В Kubernetes (k8s) правильно настроенные liveness и readiness пробы — критически важны. Chatwoot, как сложное приложение, требует проверки зависимостей. Ваша задача — сделать эндпоинт /health, который реально пингует MySQL и Redis. Если зависимость недоступна, эндпоинт должен возвращать ошибку (например, 503), чтобы k8s мог перезапустить под или временно исключить его из балансировки.

📨 2. Модуль Telegram
Здесь Chatwoot предоставляет готовую модель для подражания.

Webhook эндпоинт: Chatwoot использует выделенный эндпоинт для вебхуков Telegram. При настройке канала (Inbox) система автоматически регистрирует вебхук в Telegram, указывая URL вида /webhooks/telegram/:bot_token. Вам следует создать аналогичный контроллер в вашем Express-приложении.

Связывание Customer: Chatwoot при получении сообщения от нового пользователя Telegram автоматически создает контакт (Contact) и начинает новую беседу (Conversation). Вы можете реализовать это в обработчике вебхука: проверять наличие Customer по telegram_id и, если его нет, создавать нового, привязывая username и другие доступные данные.

Двусторонняя синхронизация: Это ключевая функция. Когда оператор отвечает в веб-интерфейсе, ваш бэкенд должен отправить сообщение в Telegram через Bot API. Когда клиент пишет в Telegram, вебхук получает сообщение, сохраняет его в БД и отправляет событие через WebSocket (например, Socket.io) подключенным операторам для обновления чата в реальном времени. Chatwoot для этих целей использует ActionCable (WebSocket).

⚙️ 3. Бэкенд и бизнес-логика
Поиск с фолбэком (Meilisearch → MySQL FULLTEXT): В Chatwoot реализован элегантный паттерн: SearchService пытается выполнить поиск через продвинутый движок (Elasticsearch/OpenSearch), а в случае сбоя автоматически переключается на резервный SQL-поиск (PostgreSQL GIN/ILIKE). Вам нужно реализовать аналогичную логику в вашем сервисе поиска: обернуть вызов Meilisearch в try/catch и при ошибке выполнять запрос к MySQL с использованием MATCH ... AGAINST.

Outbox Pattern: Это паттерн для надежной доставки событий. Убедитесь, что ваш воркер, читающий event_outbox, корректно обрабатывает ошибки. При сбое отправки уведомления (Email/TG) он должен обновить статус события на FAILED и, что важно, использовать механизм повторных попыток (retry) с экспоненциальной задержкой, который предоставляет BullMQ. Это гарантирует, что временные сбои не приведут к потере уведомлений.

SLA Pause (Бизнес-часы): Chatwoot реализует это именно так, как вы описали: если SLA настроен на работу только в бизнес-часы, таймер «замирает» в нерабочее время и по выходным. Ваш калькулятор должен учитывать рабочие часы (например, Пн-Пт 9:00-18:00). Тикет, созданный в пятницу в 17:50, должен «заморозить» свой SLA-таймер до утра понедельника. Юнит-тесты для таких пограничных случаев (пятница вечер, праздничные дни) — обязательны.

💻 4. Фронтенд и интерфейс оператора
Ваш проект использует React, а Chatwoot — Vue.js, но архитектурные паттерны применимы и здесь.

Трехпанельный чат:

Левая панель (Список чатов): В Chatwoot это компонент ChatList.vue. Он отвечает за отображение списка, фильтрацию и пагинацию. В React вы можете создать аналогичный компонент, который получает данные и управляет фильтрами.

Центральная панель (Сообщения): Компонент MessagesView.vue в Chatwoot. Ключевая задача — реализовать «прилипание» к низу (scroll-to-bottom) при новых сообщениях, но только если пользователь уже находится внизу. Это стандартная практика для чатов.

Правая панель (Метаданные): В Chatwoot эта область обычно называется "Context Panel" и отображает детали контакта, атрибуты и историю. Вы можете реализовать это как отдельный React-компонент, получающий данные о выбранном тикете и клиенте.

PWA Service Worker: В Chatwoot для этого используется библиотека Workbox, которая генерирует Service Worker для кеширования статики и обработки пуш-уведомлений. Для Vite 8 вы можете использовать плагин vite-plugin-pwa, который сильно упрощает настройку Workbox и интеграцию с вашим приложением.

🔒 5. Безопасность и валидация
ClamAV: Это правильный подход. Стриминг файла в антивирусный сканер до сохранения в постоянное хранилище (MinIO/S3) — лучшая практика. Это предотвращает компрометацию хранилища. Вам нужно будет настроить потоковую передачу файла из входящего запроса в контейнер ClamAV и принимать решение о сохранении на основе результата сканирования.

HttpOnly для Refresh Token: Это абсолютный стандарт безопасности. Убедитесь, что при установке куки для /api/auth/refresh используются флаги HttpOnly, Secure (в production) и SameSite=Strict. Это защищает токен от кражи через XSS и CSRF-атаки.

Ваш план очень близок к архитектуре и лучшим практикам Chatwoot. Ключевое отличие — технологический стек (Express/React/Prisma vs Rails/Vue/PostgreSQL), но паттерны (Webhook'и, fallback-поиск, Outbox, бизнес-часы, PWA) универсальны. 🚀 ТЕХНИЧЕСКАЯ ДОРОЖНАЯ КАРТА: TICKETSCURSOR → CHATWOOT-LEVEL
1. СТАБИЛИЗАЦИЯ ИНФРАСТРУКТУРЫ И СБОРКИ (CI/CD)
Цель: Обеспечить предсказуемость окружений и нулевой downtime при деплое, как в enterprise-решениях.
Очистка и стандартизация линтинга: Устранить 56 ESLint warnings. Внедрить lint-staged и husky для пре-коммит проверок. Добавить правило no-console в production-сборке.
Кроссплатформенный запуск: Заменить запуск-все.bat на универсальный Makefile и package.json скрипты:
makefile
  dev: docker-compose -f docker-compose.dev.yml up --build
  test: npm run test:client && npm run test:server
  lint: npm run lint:client && npm run lint:server
Hot Reload в Docker: Настроить volumes и watch режимы в docker-compose.dev.yml для Vite (фронтенд) и tsx --watch (бэкенд), исключая необходимость пересборки образов при изменении кода.
Kubernetes Health Probes: Заменить статические 200 OK на реальные проверки:
Liveness: Проверка доступности процесса Node.js.
Readiness: Асинхронная проверка подключения к MySQL (SELECT 1) и Redis (PING). Если БД недоступна, возвращать 503 Service Unavailable, чтобы k8s не направлял трафик на под.
Безопасность образов: Добавить сканирование Docker-образов через Trivy в GitHub Actions перед публикацией.
2. МОДУЛЬ TELEGRAM (OMNICHANNEL ЯДРО)
Цель: Реализовать полноценную двустороннюю синхронизацию, аналогичную Inbox API в Chatwoot.
Webhook Controller: Создать /api/webhooks/telegram с валидацией подписи (если используется Local Bot API Server) или проверкой secret_token (стандарт Telegram Webhook).
Интеллектуальное связывание (Customer Resolution):
Поиск по telegram_id.
Если не найден, поиск по @username или номеру телефона (если он был ранее сохранен).
Если клиент новый → автоматическое создание Customer с атрибутом source: 'telegram'.
Двусторонняя синхронизация (Real-time):
Оператор → Клиент: Сообщение из UI сохраняется в БД, отправляется через Telegram Bot API, статус обновляется на sent/delivered/read (через getUpdates или WebApp callbacks).
Клиент → Оператор: Webhook принимает сообщение, сохраняет в БД, и через Socket.io (комната ticket:{id}) мгновенно доставляется на фронтенд оператора с звуковым/визуальным уведомлением.
Поддержка типов контента: Обработка не только текста, но и изображений, документов и голосовых сообщений (с сохранением ссылок на MinIO/S3).
Индикаторы набора текста (Typing): Синхронизация событий chat_action (typing) между Telegram и UI оператора.
3. БЭКЕНД И БИЗНЕС-ЛОГИКА (EXPRESS & PRISMA)
Цель: Отказоустойчивость, предсказуемость SLA и расширяемость.
Meilisearch Fallback: Реализовать паттерн Circuit Breaker. Если Meilisearch недоступен (timeout или 5xx), логика автоматически переключается на WHERE MATCH(title, description) AGAINST(? IN NATURAL LANGUAGE MODE) в MySQL, с логированием ошибки в Sentry.
Финализация Outbox Pattern (BullMQ):
Таблица event_outbox: поля id, event_type, payload, status (PENDING, PROCESSING, COMPLETED, FAILED), retry_count, last_error.
Воркер BullMQ обрабатывает события с экспоненциальным backoff (например, 1м, 5м, 15м). После 3 неудачных попыток статус меняется на FAILED, и администратор получает алерт.
SLA и Бизнес-часы (Business Hours):
Создать сервис BusinessHoursCalculator, учитывающий часовой пояс компании, рабочие дни (например, Пн-Пт 9:00-18:00) и таблицу праздников.
Юнит-тесты: Покрыть кейсы: "Тикет создан в Пт 17:50, SLA 2 часа → дедлайн должен быть в Пн 10:50". Тикет не должен "протекать" в выходные.
Chatwoot-фичи (Добавить):
Canned Responses (Шаблоны): API для CRUD операций с шаблонами быстрых ответов (с поддержкой переменных, например, {{customer.name}}).
Private Notes (Внутренние заметки): Возможность добавить комментарий к тикету, который виден только агентам (флаг is_private: true в модели Message).
Audit Log: Таблица audit_logs для отслеживания действий (кто сменил статус, кто переназначил тикет).
4. ФРОНТЕНД И ИНТЕРФЕЙС ОПЕРАТОРА (REACT 19 & TAILWIND 4)
Цель: Максимальная эргономика, скорость работы и отсутствие "дерганий" интерфейса.
Трехпанельный Layout (как в Chatwoot):
Левая панель (Inbox): Список тикетов с группировкой по статусу (Open, Pending, Closed). Сортировка по last_activity_at (сверху самые свежие). Бейджи непрочитанных сообщений.
Центральная панель (Chat):
Виртуализированный скролл (или overflow-y-auto с scroll-behavior: smooth).
Автоматический scrollToBottom при получении нового сообщения через Socket.io, только если пользователь уже находился внизу (чтобы не мешать чтению истории).
Индикатор "Клиент печатает...".
Rich Text Editor (рекомендуется Tiptap или Slate.js) с поддержкой Markdown, вставки изображений drag-and-drop и упоминаний (@agent).
Правая панель (Sidebar):
Профиль клиента (имя, email, телефон, Telegram ID).
Custom Attributes (например, "Тарифный план", "ID заказа").
История прошлых тикетов и средние оценки CSAT.
PWA и Service Worker (Vite 8):
Кеширование shell-приложения (App Shell) для мгновенной загрузки.
Поддержка Web Push API для уведомлений о новых тикетах, даже когда вкладка закрыта или свернута.
Горячие клавиши (Keyboard Shortcuts): j/k для навигации по списку, e для закрытия тикета, r для фокуса на поле ввода (как в Chatwoot/Gmail).
5. БЕЗОПАСНОСТЬ И ВАЛИДАЦИЯ
Цель: Соответствие стандартам безопасности enterprise-уровня и защита от злоупотреблений.
Антивирусная проверка (ClamAV):
Реализовать потоковую загрузку: файл → временный стрим → ClamAV (через clamscan или TCP-сокет) → если чисто, загрузка в MinIO/S3 → удаление временного файла.
При обнаружении угрозы: блокировка загрузки, запись в audit_logs, уведомление админа.
Безопасность аутентификации:
Refresh Token: строго httpOnly: true, secure: true (в production), sameSite: 'strict' (или 'lax' если требуется кросс-доменное взаимодействие с виджетом).
Access Token: короткий срок жизни (15 мин), хранится в памяти (или secure cookie).
Rate Limiting: Настроить express-rate-limit на эндпоинты /api/auth/login, /api/webhooks/telegram и загрузку файлов для предотвращения DDoS и брутфорса.
Content Security Policy (CSP): Настроить строгие заголовки CSP через helmet для предотвращения XSS-атак, особенно в контексте Rich Text Editor.
GDPR / Анонимизация: Эндпоинт для полного удаления или анонимизации данных клиента по запросу (очистка PII в таблицах Customer и Message).
6. ДОПОЛНИТЕЛЬНО: АНАЛИТИКА И МОНАРИНГ (PHASE 2)
Чтобы система была по-настоящему стабильной, как Chatwoot, необходим наблюдаемый стек.
Метрики: Интеграция с Prometheus для сбора метрик: время ответа API, длина очереди BullMQ, количество активных WebSocket-соединений.
Логирование: Структурированные логи (JSON) через pino или winston с корреляционными ID (Request ID) для отслеживания запроса от фронтенда до БД.
Дашборды: Базовые метрики help-desk в UI:
First Response Time (FRT).
Average Resolution Time.
Нагрузка на агентов (количество закрытых тикетов за период).

Анализ документации Board.support выявил несколько мощных архитектурных и UX-решений, которые можно (и нужно) адаптировать в ticketscursor, чтобы приблизить его к уровню Chatwoot и современных enterprise-систем.
Вот конкретные идеи и фичи, которые стоит взять на вооружение, с переводом их в задачи для вашего стека (React 19, Express, Prisma, BullMQ).
1. Киллер-фичи UX/UI для оператора (Frontend)
Board.support делает огромный акцент на скорости работы оператора без мыши.
Продвинутые горячие клавиши (Keyboard Shortcuts):
Ctrl + ↑/↓ — навигация по списку тикетов.
Ctrl + V — автоматическая вставка скриншота/изображения из буфера обмена прямо в чат.
Esc — закрытие модальных окон или архивация текущего тикета.
Задача для React 19: Добавить глобальный хук useKeyboardShortcuts с библиотекой типа hotkeys-js.
Rich Messages (Интерактивные сообщения): Вместо простого текста, агенты могут отправлять структурированные JSON-сообщения, которые фронтенд рендерит как UI-компоненты:
Карточки товаров/услуг (Card) с кнопкой действия.
Формы сбора данных прямо в чате (Inputs, Select, Chips).
Задача: Расширить модель Message в Prisma полем content_type ('text' | 'rich_json') и rich_payload (JSONB). На фронтенде создать маппинг компонентов для рендеринга этих JSON-структур.
PWA для админской панели: Явная поддержка установки админки как приложения на десктоп и мобильные устройства (через manifest.json и Service Worker), что критично для операторов, работающих "в поле".
2. Бизнес-логика и Автоматизация (Backend)
Board.support использует концепцию "Built-in messages" (встроенных системных сообщений), которые триггерятся не вручную, а по состоянию диалога.
Умный Follow-up (Дожим): Если агент не отвечает N минут, система автоматически отправляет сообщение: "Пожалуйста, оставьте ваш email, чтобы мы могли связаться с вами, когда освободимся". Если пользователь вводит email, он сохраняется в профиль, а тикет переходит в статус "Pending".
Автоматический CSAT (Rating): При архивации тикета автоматически отправляется запрос на оценку. Если оценки нет через X часов, уходит email-напоминание со ссылкой, которая автоматически открывает чат и фиксирует оценку.
Динамические переменные (Merge Fields): Поддержка шаблонов вида {{customer.name}}, {{ticket.id}}, {{agent.name}} как в ответах агентов (Canned Responses), так и в автоматических сообщениях.
Задача: Написать утилиту resolveTemplateVariables(template: string, context: object) на бэкенде перед отправкой любого уведомления.
Объединение пользователей (Merge Users): Функция в админке для слияния двух профилей клиентов (например, один пришел с Telegram, другой с Email, но это один человек) с переносом всех тикетов под единый customer_id.
3. Производительность и Архитектура
Архивация старых сообщений (Hot/Cold Storage): Board.support переносит сообщения старше X дней в отдельную таблицу/базу. Это держит основную таблицу messages легкой и быстрой.
Задача для Prisma/MySQL: Создать воркер BullMQ, который раз в сутки переносит тикеты в статусе Closed старше 90 дней в таблицу messages_archive (или в S3 как JSON), оставляя в основной таблице только метаданные тикета.
Легковесные индикаторы набора текста (Typing): Board.support выносит это в асинхронный процесс, чтобы не спамить базу данных.
Задача: Убедиться, что события typing в Socket.io дебунсятся (например, отправляются не чаще 1 раза в 2 секунды) и хранятся только в Redis, не записываясь в MySQL.
4. Безопасность (Security)
Рандомизация имен файлов: При загрузке вложений имя файла меняется на случайную строку (например, a7f3b9_original_name.pdf). Это предотвращает прямой перебор URL и доступ к чужим файлам, даже если бакет S3 случайно станет публичным.
Задача: Модифицировать сервис загрузки в MinIO/S3: генерировать uuid для имени файла, а оригинальное имя сохранять только в метаданных объекта или в БД.
IP Ban при брутфорсе: Временная блокировка IP на 1 час после 10 неудачных попыток входа.
Задача: Использовать express-rate-limit с хранилищем в Redis для эндпоинта /api/auth/login.
5. Интеграции и Контекст (E-commerce/Data)
Хотя ticketscursor может быть не только для e-commerce, сама концепция великолепна:
Контекстные виджеты: Возможность показать в чате не просто текст, а, например, "Статус заказа: В пути" или "Купоны", подтягивая данные из внешних систем через Custom Fields.
Задача: Сделать правую панель (Sidebar) в чате динамической: если у клиента есть поле order_id, показывать кнопку "Загрузить детали заказа" через внутренний API.

Эти заимствования закрывают важные пробелы между "просто чатом" и "профессиональной help-desk платформой", делая акцент на эргономике оператора и долгосрочной производительности системы.

import { z } from 'zod';

// 1. Схема пользователя Telegram (User)
export const TelegramUserSchema = z.object({
  id: z.number().int(),
  is_bot: z.boolean(),
  first_name: z.string().min(1),
  last_name: z.string().optional(),
  username: z.string().optional(),
  language_code: z.string().optional(),
});

// 2. Схема чата (Chat)
export const TelegramChatSchema = z.object({
  id: z.number().int(),
  type: z.enum(['private', 'group', 'supergroup', 'channel']),
  title: z.string().optional(),
  username: z.string().optional(),
  first_name: z.string().optional(),
  last_name: z.string().optional(),
});

// 3. Схема сущностей сообщения (команды /start, ссылки, форматирование)
export const TelegramMessageEntitySchema = z.object({
  offset: z.number().int(),
  length: z.number().int(),
  type: z.enum([
    'mention', 'hashtag', 'cashtag', 'bot_command', 'url', 
    'email', 'phone_number', 'bold', 'italic', 'underline', 
    'strikethrough', 'spoiler', 'code', 'pre', 'text_link', 'text_mention'
  ]),
  url: z.string().url().optional(),
  user: TelegramUserSchema.optional(),
});

// 4. Схемы медиафайлов (Фотографии и файлы документов для S3/MinIO)
export const TelegramPhotoSizeSchema = z.object({
  file_id: z.string(),
  file_unique_id: z.string(),
  width: z.number().int(),
  height: z.number().int(),
  file_size: z.number().int().optional(),
});

export const TelegramDocumentSchema = z.object({
  file_id: z.string(),
  file_unique_id: z.string(),
  file_name: z.string().optional(),
  mime_type: z.string().optional(),
  file_size: z.number().int().optional(),
});

// 5. Рекурсивная схема сообщения (Message) с поддержкой reply_to_message
export const TelegramMessageSchema: z.ZodType<any> = z.lazy(() =>
  z.object({
    message_id: z.number().int(),
    from: TelegramUserSchema.optional(),
    sender_chat: TelegramChatSchema.optional(),
    date: z.number().int(),
    chat: TelegramChatSchema,
    text: z.string().optional(),
    entities: z.array(TelegramMessageEntitySchema).optional(),
    photo: z.array(TelegramPhotoSizeSchema).optional(),
    document: TelegramDocumentSchema.optional(),
    reply_to_message: TelegramMessageSchema.optional(),
  })
);

// 6. Схема нажатия на инлайн-кнопки (Callback Query для оценки CSAT / закрытия тикетов)
export const TelegramCallbackQuerySchema = z.object({
  id: z.string(),
  from: TelegramUserSchema,
  message: TelegramMessageSchema.optional(),
  inline_message_id: z.string().optional(),
  chat_instance: z.string(),
  data: z.string().optional(),
});

// 7. Корневая схема Вебхука (Update)
export const TelegramUpdateSchema = z.object({
  update_id: z.number().int(),
  message: TelegramMessageSchema.optional(),
  edited_message: TelegramMessageSchema.optional(),
  channel_post: TelegramMessageSchema.optional(),
  edited_channel_post: TelegramMessageSchema.optional(),
  callback_query: TelegramCallbackQuerySchema.optional(),
}).refine(
  (data) => data.message || data.callback_query || data.edited_message || data.channel_post,
  { message: "Инвалидный апдейт: должен содержать как минимум message, callback_query или channel_post" }
);

// Экспорт типов TypeScript
export type TelegramUpdate = z.infer<typeof TelegramUpdateSchema>;
export type TelegramMessage = z.infer<typeof TelegramMessageSchema>;
export type TelegramUser = z.infer<typeof TelegramUserSchema>;

const validateTelegramWebhook = (req: Request, res: Response, next: NextFunction) => {
  try {
    // Безопасный парсинг входящего JSON от серверов Telegram
    req.body = TelegramUpdateSchema.parse(req.body);
    next();
  } catch (error) {
    // В продакшене логируем ошибку, но возвращаем Telegram статус 200, 
    // чтобы он не спамил повторными запросами при сломанных схемах
    console.error('Ошибка валидации Telegram Webhook Zod:', error);

};
